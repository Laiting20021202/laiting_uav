## 軟體處理

已保留原本上游保護，以及開機自動執行的十秒觀察服務。紀錄分別為：

- `~/.local/state/laiting-uav/network/flight-samples.jsonl`：完整分層取樣，4 MiB 加 3 個輪替備份。
- `~/.local/state/laiting-uav/network/events.jsonl`：USB、NetworkManager、DNS、Tunnel 與網卡恢復事件，同樣最多約 16 MiB。

16:42 首版安裝的 `scripts/modem_recovery.py` 修補「介面仍 up、NetworkManager 不會自動重啟它」的恢復缺口：

1. 獨立檢查固定網卡的 MAC、USB VID／PID，明確拒絕 Hub；不選擇 ttyACM 或其他 USB 裝置。
2. 只有本地網卡閘道及兩條不依賴 DNS 的外網 TLS 連線都失敗、carrier 仍為 1、收發成功位元組至少 30 秒不增加、驅動錯誤新增至少 50 次，才嘗試該網卡的 USB device reset。
3. DNS 異常、電信外網異常但網卡閘道仍正常、仍有成功資料流、設備消失／變更，都不滿足重設條件。
4. 每次恢復間隔至少 300 秒、每小時最多 3 次；失敗的恢復也計次。同一次開機內，重新啟動服務仍保留嘗試次數。
5. 服務使用管理員擁有的獨立程式副本及 Python isolated mode，只使用標準函式庫；不重啟主機／飛控／Hub，不操作飛行命令。

這是失效後嘗試恢復的機制，不能保證 USB reset 可修好所有硬體故障，也不能保證連線不中斷。

上述為首版條件；後續已依使用者要求改為無總次數上限、涵蓋一般外網／DNS／介面消失的分階段恢復，見 [持續自動恢復部署紀錄](NETWORK_RECOVERY.md)。相機有線網路 `eno1` 明確排除於恢復操作。
