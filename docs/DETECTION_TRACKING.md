# v5 辨識與漏檢續追

2026-10-09 依使用者提供的 realtime demo 參數對齊。主設定為 `config/settings.json`，模型參數為 `models/president_cup_v5/registry.json`。

2026-10-10 依穩定優先需求，實機取樣改為 4 FPS，GUI 上限降為 2 FPS。每次處理至少休息 50 ms，推論較慢時直接跳到最新影格；以下影片重播的 20 FPS 數據為先前版本的歷史驗證結果。

| 參數 | 預設 |
| --- | --- |
| 模型 | `president-cup-v5` → `models/president_cup_v5/best.pt` |
| 實機來源 | 1920×1080，4 FPS 取樣輸出；只保存最新影格 |
| 模型輸入 | `imgsz=1280`，GPU 使用 FP16 |
| 新目標信心 | `detection.vehicle_conf=0.45` |
| 續追信心 | `detection.track_conf=0.10` |
| 漏檢保留 | `detection.track_ttl_s=0.35` 秒 |
| 一對一匹配 | 同類別且 IoU ≥ 0.15，較高信心優先 |
| NMS | IoU 0.55，最多 100 框，沿用此專案設定 |

YOLO 以新目標與續追門檻的較低值取出候選框。未匹配既有追蹤的框必須達到新目標門檻；較低信心只能續追同類別、同位置的既有目標。GUI 可修改新目標信心、續追信心及保留秒數；三項在同一次原子保存成功後立即生效，重新開機保留。新目標門檻低於續追值時，續追也使用該較低門檻。

漏檢框沿用最後實際觀測的位置及信心，顯示橘色 `HOLD` 與漏檢秒數。保留時間由最後實際觀測影格計算，保留框本身不延長壽命、不新增事件、不重算 GPS。0.35 秒內找回同一目標不會重複紀錄；到期後再次達到新目標門檻才建立新追蹤。相機更換 session 或模型成功切換時重置追蹤。

`raw` 始終顯示模型原始信心；例如 0.31 續追框仍顯示 0.31。使用者參考 demo 的 0.60 顯示追蹤分數有額外調整，原始調整公式未提供，因此本專案沒有套用該分數。兩種分數都不能直接當成辨識準確率。參考 demo 的「651 幀中 152 幀含保留框」是其既有結果，並非本機的實測值。

v5 五類是 `civilian_vehicle`、`light_tactical_vehicle`、`medium_tactical_vehicle`、`clouded_leopard_armored_vehicle`、`amphibious_assault_vehicle`。載入及 warmup 後會核對所有 registry 類別；缺少任一類別即拒絕載入，模型切換失敗保留原模型。此專案預設不優先選用舊 VisDrone `.engine`；舊模型仍可手動選擇，其類別及輸入尺寸不代表 v5。

## 各個可能類別的紀錄

目標首次符合紀錄條件時，保留同一個 NMS 框對應的所有原始類別信心。只保存目前 registry 指定且信心大於 0 的類別，按信心排序，最多 5 筆；候選類別不再套用新目標或續追門檻。即時框、最高分類別、NMS 與追蹤判斷沿用原行為，不增加推論次數。

各筆可獨立下載 JPG，包含各自的類別、原始信心與候選順位，共用觀測時間、追蹤 ID、框與 GPS；CSV 也逐類別輸出。極小正信心顯示 `<0.1%`，避免被四捨五入為零。整組紀錄在同一資料庫交易保存，失敗可在下次實際觀測重試，不會留下半組或重複的部分紀錄。每段連續追蹤只存一組；HOLD 不新增紀錄。既有紀錄無法補出過去未保存的其他類別分數，保留原內容。已內含 NMS、只提供最高分類別的匯出模型沿用單筆紀錄。

## DJI 影片重播

```bash
.venv/bin/python scripts/replay_detection.py \
  test_video/DJI_20261009124240_0568_D.MP4
```

輸出為同目錄的 `DJI_20261009124240_0568_D_v5_realtime.mp4`，以及 `.summary.json` 統計、`.detections.jsonl` 逐幀原始候選框／追蹤資料與解碼、編碼日誌。要重跑時以 `--output` 指定新檔名，避免覆寫既有結果。

這段原片主串流為 3840×2160、30000/1001 FPS、651 幀、約 21.72 秒。重播明確選擇主串流，先縮成設定的 1920×1080，再以 20 FPS 取樣；不使用 DJI 內嵌的 1280×720 次串流。輸出為 H.264 MP4，保留原片播放時間，不含原片 DJI metadata。原影片維持原檔。

重播與實機共用 `Detector`、`Tracker` 及框標註函式。逐幀時間採影片時間，以便比較保留框；離線處理所有取樣影格，不因推論慢而跳過。因此輸出 20 FPS 代表播放時間，不能宣稱 Jetson 能每秒推論 20 幀。統計另提供實測處理 FPS、平均及 P95 推論毫秒數；實機只取最新一幀，慢速推論可能增加斷追。

本次輸出為 1920×1080 H.264、20 FPS、434 幀、21.7 秒；原片 651 幀經 20 FPS 取樣後幀數減少。171 幀有實際觀測追蹤框，136 幀含漏檢保留框，兩者可重疊；共 90 個低於 0.45 的觀測框成功續追。全片逐幀核對確認：新追蹤均由 ≥0.45 的實際觀測建立，所有保留框距最後觀測不超過 0.35 秒，影片完整解碼無錯誤。

實測解碼、縮放、辨識、繪圖及編碼共約 597 秒，整體 0.73 FPS；Detector 平均約 542 ms，P95 約 1053 ms。測試時實機服務同時運作，這是本次執行的處理速度，不是獨占 GPU 的效能。辨識框統計不是準確率，也不能與原 demo 的 152／651 幀直接比較。

## 驗證與 TensorRT

已通過 164 項相關回歸測試，涵蓋低信心不建立新目標、同類別一對一續追、0.35 秒到期、保留框不定位或記錄、短暫漏檢不重複記錄、GUI 儲存成功／失敗、來源解析度與模型切換。Chromium 實測新目標滑桿、續追及保留秒數、未儲存編輯、重載、手機寬度及零 JavaScript 錯誤。

先檢查此段影片的 v5 `.pt` 結果，再在實際 Jetson 匯出 FP16 TensorRT，使用同一影片、尺寸、信心、NMS 與追蹤設定比較兩份逐幀記錄。轉換前後需比較框、原始信心、類別、漏檢、保留框與處理速度；未提供人工標註時只能比較輸出差異，無法量測準確率。

目前仍使用 `.pt`，尚未匯出或切換 v5 `.engine`。v5 的 1080p PyTorch 輸入採矩形補邊；匯出時也需核對 TensorRT 的固定／動態輸入尺寸，避免因補邊方式變更影響比對。舊 VisDrone engine 不可作為 v5 加速版本。
