## 已修正並部署

16:13 在使用者確認落地後，執行 `scripts/services.py --tunnel-only`：

1. **重建前檢查上游。** 公網探測連續失敗，或 Tunnel 沒有 ready connection 超過期限時，先檢查服務實際使用的 DNS（edge SRV、網站 A、SSH A），以及不需 bootstrap DNS、驗證 TLS 憑證的獨立 HTTPS DNS 查詢。上游也壞時保留現有程序，讓 cloudflared 自行重連；上游恢復但 Tunnel 仍壞時才重建。路由改變／長時間無路由的原有處理保留。
2. **HTTP 健康檢查有 HTTPS DNS 備援。** 一般 DNS 解析失敗或連線逾時後，透過 `https://1.1.1.1/dns-query`、`https://8.8.8.8/dns-query` 依序重試，保留網站與 DoH 的憑證驗證。HTTP／憑證錯誤不當成 DNS 問題。這是健康檢查的備援，並未把 cloudflared 的所有 DNS 查詢改成 DoH。
3. **獨立保存分層證據。** 新增並 enabled `uav-network-health.service`。健康時每輪結束後等 60 秒、異常時等 15 秒，並行記錄一般 DNS、兩個上游的 UDP／TCP SRV、兩條不依賴一般 DNS 的 HTTPS 查詢。此服務只讀取，不重設網卡。既有持久 recorder 同時納入這些結果與 `systemd-resolved`，容量維持最多約 16 MiB。

原判斷沒有分辨「健康檢查使用的 DNS 故障」與「Tunnel 故障」。此次修正避免因上游異常而主動終止可能仍有用的連線；`/ready` 的數字可能過期，因此不能聲稱 15:52 當時的舊 Tunnel 一定還能傳輸。

UAV 主程式 PID 1632、NRestarts=0 維持不變；主機 resolver SHA256 與路由表比對相同。未重開主機、重設 USB、改動飛控或停止飛行紀錄。

## 尚未消除的飛行中風險

本次修正是軟體恢復判斷的補強，沒有證明網卡／電信路徑根因已排除。USB 網卡省電目前已是 `power/control=on`，不能再把「關閉省電」當成本次修復。

要降低飛行中失聯風險，需要實際配置獨立備援鏈路並驗證：至少不同電信的另一條上網路徑、適當的天線位置和供電、網卡／USB 接頭或 Hub 的替換比對，以及落地狀態下的實體斷網與負載持續測試。一般雙 WAN 切換可能中斷既有 TCP session；若要求影音／遙測盡可能連續，需另行設計並實測多路傳輸或保持連線的方案。飛行控制的失聯處置須獨立於此網站連線，由飛控／遙控鏈路配置並驗證。

目前 Wi-Fi 未連線，沒有第二條已驗證的上網路徑。短時間通過探測不代表已完成飛行可靠度驗收，單一行動網路也無法承諾零斷訊。
