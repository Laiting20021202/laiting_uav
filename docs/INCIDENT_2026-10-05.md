## 當場重現的 DNS 問題

- 12:45、12:54、後續比對中，一般 curl 反覆出現解析逾時；保留 HTTPS hostname／TLS 驗證、以已解析位址指定連線時，公開 `/healthz` 約 0.35 秒回 200。
- 直接獨立查詢公共 DNS 的 A、AAAA、SRV 大多在 0.03–0.10 秒完成；行動網卡提供的 `192.168.125.1` 對部分查詢逾時。
- 用同一個 UDP socket 同時查 A／AAAA，對 `8.8.8.8`、`1.1.1.1` 曾只收到 A 回覆；改成分開查詢可收到兩類回覆。設定 `single-request-reopen` 後 curl 實測恢復。
- 以上支持目前 DNS 路徑存在丟失查詢／回覆的問題；未做封包擷取，不能進一步確定是網卡韌體、NAT 或電信網路。此項重現也不能單獨證明 12:25 整段故障只有 DNS 一個原因。

Cloudflare 官方文件指出 SRV 查詢逾時會阻止 Tunnel 找到 edge，並建議在本機 resolver 異常、公共 resolver 正常時改用可靠的公共 DNS。[官方排障](https://developers.cloudflare.com/tunnel/troubleshooting/)

## 已部署修改

1. `scripts/tunnel_dns.sh` 以 rootless user／mount namespace，讓 Tunnel 及其 SSH／HTTP 探測共用專用 resolver；`1.1.1.1` 優先、`8.8.8.8` 備援，`timeout:1 attempts:2 single-request-reopen`。主機 resolver SHA256 前後相同，VPN／路由及影像程式未修改。
2. 除 SSH banner 外，新增公開 `/healthz` 檢查；本機 health 正常、公網連續三次失敗才重建。SSH／HTTP 分別累計失敗，避免不同原因混算；本機服務異常不觸發 Tunnel 重啟。
3. 啟動寬限由 45 改為 20 秒，正常探測間隔由 60 改為 15 秒；失敗複查間隔仍 5 秒。探測耗時另計，不能宣稱固定 15 秒恢復。原路由穩定檢查、短暫離線寬限、systemd 自啟和重啟機制保留。
4. 持久網路紀錄納入公開 HTTP 健康結果，方便下次分辨網站、SSH 及本機狀態。

12:59:52 開始套用；13:00 Tunnel 已重新建立四條 edge connection。`uav-v2` PID 保持 1767，`NRestarts=0`。
